## 3. Benchmark Target Table (Pre-approved, ADR-016)

Defined from engineering first principles **before** any R3 measurement. The Huawei/HarmonyOS 83 ms inference figure in `M0-C.md` is a *data point*, not a basis. Full table also lives in `ADR-016` §"Pre-approved Benchmark Targets".

| # | Metric | Target | Failure threshold | Window | Device |
|---|--------|--------|-------------------|--------|--------|
| 1 | Effective observation rate | ≥ 28 obs/s | < 20 obs/s | 60 s | iOS+Android |
| 2 | Inference latency p50 | ≤ 40 ms | p50 > 55 ms | ≥300 inf | iOS+Android |
| 3 | Inference latency p95 | ≤ 60 ms | p95 > 80 ms | ≥300 inf | iOS+Android |
| 4 | Observation-to-display p95 | ≤ 100 ms | p95 > 150 ms | sustained | iOS+Android |
| 5 | JS responsiveness / JS load | 0 long tasks >50 ms from pose path | >3 long tasks/s or any >100 ms | 60 s | iOS+Android |
| 6 | Overlay smoothness | ≥ 50 fps, <2% dropped UI frames | <40 fps or >5% dropped | 60 s | iOS+Android |
| 7 | Thermal trend | no throttling ≤10 min; ΔT ≤8 °C | throttling or ΔT >12 °C | 10 min | iOS+Android |
| 8 | Memory stability | ±10% over run, no OOM | >20% growth or OOM | 10 min | iOS+Android |
| 9 | Tracking recovery | ≤1.5 s resume | >3 s or restart needed | ≥5 cycles | iOS+Android |
| 10 | Model/profile load | load ≤3 s; first valid ≤5 s (warm) | load >6 s or first valid >10 s | ≥5 starts | iOS+Android |
| 11 | Background/foreground recovery | resume ≤2 s, correct state | >4 s or stuck/restart | ≥5 cycles | iOS+Android |

**Three layers per metric:**
- **TARGET** — value R3 evidence should meet for ADR-016 candidate acceptance in R4.
- **MEASUREMENT METHOD** — see ADR-016 definition column; collected via benchmark harness on representative iOS+Android devices with canonical M0-M fixtures + active Squat profile.
- **PASS/FAIL RULE** — candidate passes a metric if measured value meets TARGET and does not breach FAILURE; breaching FAILURE → no-go for that metric (exclusion needs recorded technical evidence per C5).

---

## 4. Rationale for Every Target

1. **Effective observation rate ≥28 obs/s** — Squat motion cadence is slow; 28–30 fps gives smooth phase/rep detection with margin. Below 20 fps analysis becomes coarse.
2. **Inference p50 ≤40 ms / p95 ≤60 ms** — keeps a 30 fps frame budget with headroom for transport + engine; tail must stay bounded. Based on MediaPipe Pose Landmarker typical ranges, set from budget math, not from the 83 ms data point.
3. **Observation-to-display p95 ≤100 ms** — keeps overlay visually coupled to motion (<100 ms perceived coupling).
4. **JS responsiveness** — UI must stay interactive; bridge/transport must not monopolize the JS thread (RN performance guidance).
5. **Overlay smoothness ≥50 fps / <2% dropped** — smooth visual feedback; 60 fps UI target with margin.
6. **Thermal trend** — must sustain a workout-length session without throttling; aligns with M0-ENG-007 pre-approved-target concept and device thermal envelopes.
7. **Memory stability ±10%** — long sessions must not leak (mobile memory hygiene).
8. **Tracking recovery ≤1.5 s** — user movement mid-set is expected; recovery must be fast and not require restart.
9. **Model/profile load ≤3 s / first valid ≤5 s** — acceptable startup; MediaPipe model load typical 1–3 s.
10. **Background/foreground recovery ≤2 s** — interruption handling must be robust (M0-B lifecycle design).
